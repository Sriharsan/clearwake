One loop, every case

Item not received, from shipping to two receipts.

Every part of Clearwake is a step in this one sequence. No step is a separate product.

  1. 0

    Rules, set once, in plain words

    The merchant says the limits out loud. The buyer sets what their agent may claim. After that a model can propose anything, and it can never go past the signed rules.

  2. 1

    Prevention

    When the merchant ships, Clearwake adds the tracking to PayPal through the Add Tracking API, so the order is ready to defend before any dispute exists.

  3. 2

    The buyer's agent watches

    When the tracking stalls past the expected date, it opens the item not received dispute in PayPal, inside its mandate. It can only claim for orders its mandate covers.

  4. 3

    The merchant's agent reads

    The dispute, the order, the tracking on PayPal, and the signed dispatch record, with the photo count where there is one.

  5. 4

    The model drafts, the rules decide

    Delivered with proof: send the evidence. In transit: message the buyer's agent with the tracking and a date. Not shipped, lost or short shipped: offer a refund or a partial settlement inside the merchant's limits, sent alone. The buyer's agent accepts only what its mandate allows.

  6. 5

    Both sides read PayPal's record

    Until it says RESOLVED. A lost response is never retried blindly, and nothing is ever paid twice.

  7. 6

    Two signed receipts

    One from each side. Both name the same PayPal dispute id, and both verify offline.

Step zero

Say the rules once, in plain words.

The merchant says it out loud. Typing works too.

Settle an item that has not arrived on its own up to USD 5.00. Ask me from USD 5.01 up to USD 9.00. Never more. Send evidence when the records answer the claim. Every other dispute reason goes to me untouched.
Claim only for an order this agent placed, up to its amount.
  1. A local model turns the sentence into a policy.
  2. The system reads it back in plain words, written by code from the checked policy, so what you hear is what is enforced.
  3. The merchant says yes, and the policy is signed.

Ask by voice what happened today. The answer comes from the receipts only. Approve by voice only when the signed policy allows it. On a phone, run python -m clearwake --phone and scan the code.

Every figure in a sentence must be one the person said. A limit the sentence never named is refused.

Settled in conversation

The wake of one dispute. Each ring is a signed step.

Case n, 3 Nov 2026. Scroll, and the rings follow the five signed receipts of dispute PP-R-OBG-10196144. Pick any step and change one value in it: your browser checks every signature and hash with WebCrypto, and the wake shows where it breaks. Nothing is uploaded.

Checking the receipts.

  1. Buyer

    A dispute opens.

    The sandbox buyer opened PP-R-OBG-10196144 in PayPal's Resolution Center. The buyer's own words were not saved in the recorded run, so none are shown.

  2. Receipt 1, decision

    The policy decides.

    The agent proposes settle_by_offer (scripted, not AI). The policy agrees: offer USD 2.50, inside the owner's limit of USD 5.00, no approval needed (approval above USD 3.00, from policy/merchant.yaml).

  3. Receipt 2, decision

    The same decision, recorded again.

    The run was repeated before the offer went out, and the decision came out the same. The policy hash is identical in both receipts.

  4. Receipt 3, offer sent

    One offer, sent alone.

    "We are sorry about this order. To settle it now, we offer a refund of 2.50 USD". Wording from clearwake/swarm.py. It goes as an offer alone, because PayPal refuses an offer after a seller message.

  5. Receipt 4, PayPal read

    PayPal's record is the judge.

    PayPal reads UNDER_REVIEW at INQUIRY. Nothing is counted as settled until PayPal's own record says RESOLVED, so the receipt waits.

  6. Receipt 5, PayPal read

    Resolved, no claim, no fee.

    The buyer accepted in PayPal's Resolution Center, because this app cannot act for the buyer. PayPal paid refund 0TB11858A85953644 and reads RESOLVED (RESOLVED_BUYER_FAVOUR) at the INQUIRY stage.

Inside and outside

One gateway out, and only to the PayPal sandbox.

Inside

  • Dispute text, buyer messages and evidence drafts
  • The policy file, the approvals and the limits
  • The local model and the signed receipts

Agents have no route out. In case m their DNS lookups fail.

Outside, through one gateway

  • Only api-m.sandbox.paypal.com is allowed (policy/merchant.yaml)
  • Only what the PayPal call needs: a message, an offer amount, tracking facts
  • Any other host is refused and receipted. In case m, example.com got a 403

The gateway's 34 receipts from that run are published with the others. The hosted site you are reading runs no agents and is not inside this boundary.

The 1.5% line

Drag the mercury. Watch the fee double.

A seller with more than 100 sales in the previous 3 months and a dispute rate of 1.5% or more pays the High Volume Dispute Fee on every dispute: USD 30.00 instead of USD 15.00. PayPal Merchant Fees, US, updated 1 Oct 2026. The rule and both fees are the ones in clearwake/fees.py.

The recorded sandbox has a handful of test orders, far under 100 sales, so the rule does not apply to it. The figures here are example values for you to change. They are not Clearwake results.

How to run it

Python 3.12 or newer. Nothing to install.

It starts on local records and makes no network calls.

git clone --recurse-submodules https://github.com/Sriharsan/clearwake.git
cd clearwake
python -m clearwake --port 8810

Then open http://127.0.0.1:8810/console. Speak to it from a phone with python -m clearwake --phone. The network isolated run (case m) needs Docker and your own sandbox keys: python scripts/airgap.py. Check a receipt log with the network off: python -m verdock_core verify <log.ndjson> --public-key <64 hex characters>.

Disputes that end in a conversation do not end in a fee.
